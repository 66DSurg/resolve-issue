# Lessons catalogue

Every lesson that `resolve-issue` encodes, merged from about 600 raw notes gathered over months of agent-driven work on one production app. The wording is general so it applies to any project. Each lesson reads **rule**, then the reason, with a one-line origin story in brackets.

Built while making Case Logbook (caselogbook.com) by Dr Biswajit Dutta Baruah.

How to use this file: every lesson has a stable id, the section code plus its number (`DG-7` is Diagnose lesson 7). The stage references cite these ids next to the instruction that applies each lesson, so you can always trace a rule back to the incident that created it. This file is the CORE catalogue, the rules that hold for any project. Lessons that encode one product's taste or one domain live in `references/packs/*.md`, keep their ids, and load only when their pack is switched on; a line here marks where each went. When a run teaches you something new, append it to the right section in the same format, with the next free number (see DC-21), and cite it from the stage reference that should apply it. `scripts/check.py` fails if a core lesson is not cited anywhere. A lesson that no longer earns its place is archived or moved to a pack, never deleted, and its id is never reused (SKILL.md, "Feed the lessons back").

In the origin stories, "the operator" is the solo developer the lessons came from.

## 1. Pre-flight (PF)

1. **Create the tracker issue before any fix starts, quick hot-fixes included, and cite only issue numbers that exist. If a run defers work to "#NN", check that #NN exists.** — Untracked fixes leave no history. (Commits cited six invented issue numbers, and the operator said of hot-fixes made without issues: "now there is no track of all that we solved".)
2. **In nested repositories, run `git remote -v` before writing paths or deploy config. Never apply a parent repo's settings to a child repo.** — The wrong repo silently builds the wrong source. (Deploy configs repeatedly picked up the parent repo's remote and path prefixes.)
3. **Ask only the questions that change what gets built. Ask them one at a time, each with a recommended answer. Otherwise start, and write your assumptions into the spec.** — Long lists of questions stall decisions. (This was the operator's working pattern throughout. Background diagnosis started right away unless a choice changed the build.)
4. **Read prior decisions (ADRs, decision notes, memory) before proposing a design, and flag any conflict with a locked decision.** — Reversing a decision silently means repeating a mistake that was already settled. (A storage spec picked a vendor for sensitive media that an earlier firm decision had ruled out, and the spec had to switch late.)
5. **When a request contradicts a shipped architectural stance, state the contradiction and why the stance exists, then get an explicit decision.** — The stance usually protects something the requester has forgotten. (An "auto-merge look-alike records" request would have reversed a "completeness over hard dedup" decision made so that imports never destroy a real record.)
6. **Treat memory and old notes as possibly stale. Check each claim against current code and mark items "possibly open", never assume they are done.** — Notes drift away from the code. (A queued "fix" turned out to be built and wired already, while two related items were still unverified.)
7. **Check that a dependency is feasible before speccing it: is the package maintained, does its latest code still have the bug, is the wrapper alive as well as the engine?** — Finding out it is impossible halfway through the build wastes the build. (One model was alive but its npm wrapper was dormant and broken, and the latest release was a year stale.)
8. **Inspect seed and reference data before assuming what it contains.** — A wrong assumption reshapes the whole design. (A scraped seed was assumed to hold national distributions. It held names only.)
9. **Measure an external data source's quality before building on it.** — A cheap measurement saves you from seeding junk. (An open map dataset for one region was about a third junk and missing the operator's own institution.)
10. **Treat a token's write access as unavailable until a write actually succeeds.** — Notes about access go stale. (An integration recorded as "full read+write" was read-only, so deploy triggers and cache purges failed.)
11. **Pass the human's verbatim report and screenshots to every stage as readable file paths.** — Paraphrase loses the detail that tells the real symptom from a neighbouring one. (Several runs fixed a neighbouring symptom after the report had been summarised.)
12. **Check a dependency against every platform the product targets (desktop, Android, iOS, each browser) before choosing it. "Works on one platform" is not feasible.** — A single-platform pick silently drops whole groups of users. (An on-device speech engine was proposed in the same breath as one mobile browser, which would have left desktop and Android users out of a product meant to work for anyone, anywhere.)

## 2. Diagnose (DG)

1. **Before committing to a root cause, write the symptom, list every candidate cause (your favourite included) and force a relative ranking. Never ask a model, or yourself, "is my hypothesis right?"** — Yes/no judgments are unreliable, while forced ranking is reliable. (On historical bugs with known causes, absolute "is this sound?" judgments scored 2/4 and rated a known-wrong cause sound at 0.77. Relative ranking scored 6/6, picking the real cause 0.95 vs 0.03 and 0.74 vs 0.04.)
2. **Build "rank, don't confirm" into the tool: a ranking helper refuses to run with fewer than two options, and it batches independent questions into one call.** — A single option quietly turns the question back into "am I right?". (The helper script errors on one option because yes/no mode measured so badly.)
3. **A ranking informs and never decides. Still read the code, probe and measure. When evidence and ranking disagree, evidence wins: say so and record the overrule.** — A ranking is not evidence. (A ranker put "this repair path never runs" at 0.73. A measurement showed it ran twice per unlock.)
4. **When you learn a new fact, ask for the ranking again with that fact included.** — Rankings are only as good as their inputs and can flip completely. (A "checksum-only" storage option fell from 0.65 to 0.00 once a fresh-CI vs long-lived-production divergence was added to the prompt.)
5. **When you score a ranking tool on past cases, have someone who does not know the answer write the distractors.** — The correct option tends to be the most specific one, which inflates scores. (A 6/6 retrospective score was judged softer than it looked for this reason.)
6. **Use the strongest model and the highest effort for diagnosis.** — A wrong diagnosis costs a whole build cycle, and diagnosis needs only one or two agents. (Three confident, wrong hypotheses in one month each cost a full build workflow.)
7. **Diagnosis method: (1) trace the real code path end to end, with file:line; (2) list every candidate cause; (3) rank them; (4) gather evidence that tells the top candidates apart, ideally a failing test or scripted repro; (5) state the confirmed cause, or say which candidates remain and what would settle them. Do not fix anything during diagnosis.** — Skipping steps produces confident wrong answers. (Three diagnoses in a row on the same area were wrong.)
8. **Do not theorise. If reading the code cannot settle a question, write a probe (a temporary test or scratch script), run it, and report MEASURED values along with the method used.** — Mechanisms that sound plausible are often wrong. (A text-wipe bug blamed on whole-field selection was refuted by watching the caret in a real browser. A detector's blind spot was found only by running the real detector over the exact rows.)
9. **Return diagnosis as structured output: method, findings, evidence, candidates (each with a verdict and evidence), ruled_out, open_questions, confidence.** — Free text hides weak evidence. (A schema forced explicit "ruled out" and "still open" lists that the spec stage could check.)
10. **Seed the diagnosis prompt with an "ALREADY RULED OUT, do not re-investigate" list and a "KNOWN SUSPECTS, confirm or eliminate each" list from earlier attempts.** — Otherwise the most expensive stage re-checks causes already disproven. (Repeat attempts on one surface kept re-investigating them.)
11. **When a surface has failed before, say so ("this is the FOURTH attempt") and make the agent read the earlier issues, specs and plans first.** — Each fresh attempt otherwise repeats the old mistakes. (A recurring bug was re-diagnosed from scratch three times.)
12. **Run independent diagnosers in parallel on different angles, such as "what the component receives" and "where two paths diverge". The spec agent reconciles them and reads the code itself where they disagree.** — Different angles find different causes. (A detector bug surfaced by comparing the path that rendered data correctly with the path that silently missed it.)
13. **When one code path works and its sibling fails, diff the inputs each sends to the shared dependency.** — The single difference is usually the whole bug. (Biometric unlock worked and biometric sign-in failed. One passed an explicit credential allowlist, the other an empty one.)
14. **Reproduce through the real entry point (a page, or a harness that clicks and dumps the DOM), varying one input at a time until the symptom appears. Keep the reproduction as the regression test and delete throwaway probes.** — Logic-level tests miss render-level bugs. (Detector unit tests were green while the real page showed a blank section in production.)
15. **Check that the fix targets the symptom that was reported, not a neighbouring one. Ask the reporter the one question that tells them apart (which screen, which flow), and keep the issue open until they confirm.** — Real fixes for the wrong bug still leave the user broken. (A release shipped a genuine fix for a bug the operator did not have. The duplicates they did see were found weeks later.)
16. **For silent failures where the endpoint always reports success (anti-enumeration, fire-and-forget), check the cheapest precondition first: does the exact input, byte for byte, match a real record?** — Providers, DNS and env are expensive to check and rarely the cause. (A sign-in email "never arrived". Twenty minutes went on the email provider and proxy logs before the typed address turned out not to match any account.)
17. **If a test runner hangs with no output, run one trivial known-good test file. If it passes, the runner is fine and a specific test is hanging, so bisect by file.** — Blaming the machine burns sessions. (Two sessions blamed the runner and a CPU-pegged file watcher. The cause was an infinite reactive loop in a component.)
18. **Read the failing SET of tests, not the count. To decide what was pre-existing, check out the pre-change commit and run exactly those specs.** — Failures spread across unrelated areas are environmental, and a new failure in the area you changed is a regression. (Five e2e failures were proven environmental by reproducing the same five on the baseline.)
19. **When an AI/model call returns empty or wrong output with no error, treat the model as a variable: swap one model at a time, keep everything else fixed, and verify any model change with a real-API end-to-end test.** — Mocks cannot catch model behaviour. (A newer model id returned empty extractions on the project's key with no error logged.)
20. **Establish the root cause from evidence before blaming anyone: read each agent's actual commands and the timing of the symptom.** — "It must have been the agent" is a guess. (259 tracked files vanished after a background run. The transcripts showed only read-only commands, which placed the cause in the runtime's teardown.)
21. **Confirm a data defect on a second, independent dataset before planning the fix.** — It tells you whether the defect is systematic, which allows one combined correction. (Two years of uploads showed the same three extraction gaps.)
22. **Fix missing upstream inputs before touching downstream displays. Treat a contradiction in generated output as a sign of missing input.** — One absent value can poison many derived metrics. (Operative times that were never read produced zero hours, then impossible rates, then a headline that contradicted itself.)
23. **Behind repeated symptoms, look for the structural cause: the tool, runner or process that forces the bad pattern.** — Fixing instances one at a time never ends. (Database functions were redefined up to six times in migration history because the runner could apply a file only once.)
24. **When behaviour depends on a framework's internal timing, reproduce the bug and read the dependency's source before choosing a fix.** — Guesses about the internals are usually wrong. (A history pop cancelled an in-flight navigation, and the router's "navigating" flag was set only after an await.)
25. **Once a cause is found, search for siblings of the same class and fix them at the shared seam, not only on the path the ticket names.** — Series of hot-patches usually come from one pattern repeated in several places. (Four consecutive hot-patches were siblings, and a stale-ciphertext crash appeared in three paths until one shared decrypt helper was guarded.)
26. **Before applying a "one-line fix", ask what it newly arms downstream (constraints, indexes, triggers), and trace the new failure path.** — Small changes can switch on dormant machinery. (Writing an identity hash would have armed a unique index for the first time. A second same-day record would then be "deduped, 200 OK": silently dropped while the user was told it saved.)
27. **When you find a bug, look for the test that asserted the dangerous behaviour as correct.** — A passing test built on the wrong data shape can enshrine a bug. (An "anti-collision" test used two genuinely different people, so the dangerous same-person case was never tested.)
28. **When users keep reporting the same logic as broken, add a self-explaining diagnostic ("why weren't these two grouped?") that shows the keys and the failing comparison, without leaking private data. Ship it alongside the root-cause fix.** — Then the next report carries its own evidence. (Three rounds of wrong theories about grouping each cost a workflow.)
29. **In agent prompts, search with the real grep binary (`command grep`) or another locale-safe search.** — Shell wrappers can silently skip files they misdetect as binary. (A source file containing em-dashes was skipped, so a symbol looked absent.)

## 3. Spec (SP)

1. **For a multi-slice feature, grill the next slice against the glossary, the ADRs and the original design before speccing it. Then run spec, plan and build in one background run, without stopping for a plan review.** — Without this, later slices drift from the earlier ones. (A media feature's first slice drifted from the core model. Grilling produced three ADRs and a revised slice order.)
2. **Feature issues get a design grill. Plain bugs go straight to the pipeline. Deferred work stays eligible for ranking: express deferral through priority, never by hiding the issue.** — Hidden issues get forgotten. (Deferred features were excluded from next-up ranking, which the operator said was wrong.)
3. **If no diagnosed mechanism actually produces the reported symptom on the reported data, the spec says so. It then specifies the measurement still needed, or a fix that is correct regardless plus in-product evidence capture.** — Never paper over the gap. (A fix that passed every test would not have changed the user's exact rows.)
4. **Spec rules: fix the root cause in the shared place every caller routes through, with the smallest change that fully resolves the symptom. Include exact user-facing copy, tests (one of which fails before the fix), docs impact, what is deliberately NOT changed, and honest risks.** — Patching only the named page leaves sibling callers broken. (Three input surfaces shared one buggy helper.)
5. **Keep scope to what was reported. Put adjacent cleanup into separate, numbered follow-up issues.** — Widening a change restyles screens nobody reported. (Migrating every toggle at once was rejected. The follow-ups shipped one at a time.)
6. **Mark scope boundaries explicitly: in scope, EXPLICITLY OUT OF SCOPE, and things the agent cannot validate (real devices, hardware), which are flagged for a manual check and never faked.** — Agents otherwise claim behaviour they cannot test. (Agents claimed real-device results from a laptop.)
7. **If a change contradicts an existing ADR, say so in the form "Contradicts ADR-NNNN … but worth reopening because …". Never silently override it.** — Silent overrides corrupt the decision record. (This is the domain-docs contract.)
8. **Use the project glossary's terms in issue titles, hypotheses, test names and specs. Treat a missing term as a signal: either you are inventing language or there is a real gap to record.** — Synonym drift makes specs, code and docs disagree. (Specs used words the codebase did not.)
9. **Before introducing a domain term, check that it does not collide with an existing one.** — Near-identical names for different concepts confuse users and agents. (A proposed "teaching set" would have sat beside an existing, different "teaching file".)
10. **Specs and plans are design artifacts, not the queue. Never track live issue state in local Markdown.** — Local copies of the queue drift. (The project keeps one queue of truth, in the tracker.)
11. **Never build a destructive or data-loss-sensitive path from a vague request. Have diagnosis produce a "decision required" menu of options, each saying what survives and what is lost, for a human to choose.** — The irreversible choice belongs to the human. (A password-reset request collided with a zero-knowledge design.)
12. **For data-sensitive changes, write the load-bearing invariant and its catastrophic failure mode into the spec (e.g. "absent stamp = adopt, never wipe"), and make its tests the gate.** — The obvious implementation is often the catastrophic one. (A naive owner check would have wiped every existing user's local data on first deploy.)
13. **Give agents a file map of the key files and an exemplar spec to copy the house format from.** — Agents without a map wander, and format drift makes specs hard to review. (Early specs varied wildly in shape.)
14. **Write standing rules as numbered NON-NEGOTIABLE LAWS ("violating any fails the task") and give the verifier the same list to check mechanically.** — Soft guidance gets ignored under pressure. (Numbered laws that the verifier enforced were reliably respected.)
15. **When several inputs feed one capability, give each input its own spec but have them all write to one shared, source-agnostic store.** — One store means one set of views. (Spreadsheet import and manual entry both feed one finance store.)
16. **Keep "does this apply to this user?" (hide it) separate from "has this user paid?" (lock it).** — Merging the two muddles both. (Role hides a module, and subscription controls access to it.)

## 4. Plan (PL)

1. **Before launching a build, check that the plan fixes the reported symptom and not a neighbouring one. Ask it as an explicit ranking question against the alternatives.** — A build is the most expensive place to discover the mismatch. (A release fixed a real bug the operator did not have.)
2. **The plan is where each build task's code gets written. Give it top-tier reasoning and put ACTUAL code, exact signatures and checkbox TDD steps in it: write the failing test, run it and SEE it fail, implement, see it pass, run checks, commit. Ban "TBD", "add appropriate handling" and "similar to Task N".** — Plan errors multiply across every task, while concrete plans let a cheaper builder simply apply them. (The first tiered run had one rejection, an unticked checkbox, and no code faults.)
3. **The plan returns its units as structured data (id, title, files, depends_on, instructions, acceptance), also saved to a file in the repo. The build iterates over that list. Never hardcode build units in a script written before the plan exists.** — Hardcoded lists drop units. (Scripts written before planning built fewer units than the plan defined, and half-features nearly shipped.)
4. **Tasks in the same parallel wave touch DISJOINT files. The verifier enforces this with a scope check (`git show --stat HEAD` shows only the task's files).** — Parallel builders on shared files clobber each other. (Overlapping builders overwrote each other's edits.)
5. **Decompose into small tasks, mark which are independent, run independent tasks in parallel and dependent ones in series. Each task gets its own verifier and repair loop.** — This is the process that worked across the whole project. (The operator had to restate it several times before it became the default.)
6. **Split big issues into linked sub-issues and fix the smallest first.** — Small units finish and give early signal. (Decomposition was the planning step of the proven loop.)
7. **Cap the task count (aim for 3 to 9, slice hard at about 10). Order the tasks: root fix first, then diagnostics and guards, then docs.** — Unbounded plans balloon cost, and this order fixes the user's symptom even if later tasks fail. (Plans without caps grew past 15 tasks.)
8. **Prefer the fix that works with already-deployed state over a "cleaner" one that strands existing users or data.** — Real users already hold the old state. (Flipping a credential setting would have stranded every passkey already enrolled on real phones.)
9. **Remove a buggy, low-value path rather than sink time into fixing it.** — Deleting code is the cheapest fix. (An unreliable photo-OCR path broke record creation and was removed.)
10. **Architecture reviews: scan the whole codebase, produce a visual report, grill the chosen candidate against the code, record an ADR, file an issue, then build.** — A "strong" candidate can collapse under grilling. (One candidate turned out to be correctly different code, while another exposed a real bug.)
11. **When ranking a queue, include untriaged items that the default ordering cannot rank.** — Otherwise they are invisible. (The pinned queue sorted only labelled issues.)
12. **Re-rank the queue every one to three resolved items in a long campaign instead of following a fixed plan.** — Priorities shift as you learn. (A 29-issue refactor campaign was re-ranked every 1 to 3 items.)
13. **Track every follow-up from a long saga as a real issue until it is done.** — Long slices make people forget them. (The operator said dropped follow-ups leave "a gaping hole".)
14. **When a ranked queue surprises the human, audit its inputs (labels, priority fields, the rubric) before defending the order.** — A strange order is usually a bad input, not a deep insight. (A cosmetic issue sat above serious ones, and the operator rightly asked whether the queue worked at all.)

## 5. Sizing and budget (SZ)

1. **Scale effort to the issue's size. Announce the size estimate and the agent count before starting. A small issue gets one builder and one verifier.** — Unscaled runs burn budget on trivia. (A single issue consumed 1 to 4 million subagent tokens.)
2. **Respect declared concurrency caps (e.g. at most 3 runs at once, and 1 at a time after hitting a usage limit until it resets). Count the running jobs before launching, queue the rest as issues, and say which slot each one is waiting for.** — Too many runs exhaust the budget mid-run. (The operator was "burning a lot of cash" and hit the usage limit.)
3. **Batch several small, independent issues into one run: a build→verify→fix→re-verify pipeline per item, then one shared gate and one docs pass.** — Batching cuts overhead while keeping per-item verification. (Three quick wins in one run cost less than three workflows.)

## 6. Orchestration (OR)

1. **Default pipeline, applied without being asked: Diagnose → Spec → Plan → Build (in parallel where independent) → adversarial Verify per task, with a repair loop → Gates → Docs (only if affected) → Summary → STOP before push, tag or release. Each stage is a separate agent, and its output passes verbatim into the next stage's prompt.** — Single-blob runs took hours and hid failures. (About 70 ad-hoc workflows converged on this shape.)
2. **Run issue work in the background so the conversation stays free.** — Inline edit-gate-commit blocks discussion. (An issue done in the foreground was called wrong.)
3. **Keep ONE canonical workflow template and stamp per-issue copies from it with a tiny script. Never hand-edit the copies, and put all per-issue variation in launch args.** — Hand-edited copies drift. (38 per-issue files were byte-identical apart from the name, but only because a script generated them.)
4. **Put the issue id in the run's display name. If the runtime requires the name as a literal, generate a per-issue copy.** — Otherwise concurrent runs are indistinguishable. (Three runs all showed "issue-fix": "how do I identify them?")
5. **Parameterise through launch args: issue ids, branch, worktree path, the human's report, screenshot paths, extra context docs, diagnose and spec focus, spec path, ports, whether e2e is allowed, env file path, commit tag, decision-helper path, model-tier table.** — One template can then serve very different issues. (A single file served dozens of issues.)
6. **If workflow scripts cannot read files, the orchestrator reads the config (model tiers, project profile) and passes it in as args. The config file stays the single source of truth, and each run carries a copy.** — Tiers hardcoded in scripts drift. (Tiers embedded in scripts diverged from the table.)
7. **Inject one shared preamble into EVERY agent prompt: working directory and branch, forbidden actions, the privacy rule, where context lives, the decision rule, port and server rules, how to source the test env, doc locations, commit format and trailers, and files never to stage.** — Subagents start with no context. (Every rule that lived only in the orchestrator's head was violated by some subagent.)
8. **Wave scheduler: run every task whose dependencies are done in parallel. If nothing is ready (a cycle or a bad id), run the first remaining task alone. Treat a dependency id that is not in the plan as satisfied.** — Planner graphs are sometimes inconsistent and must not deadlock the run. (Several plans contained cyclic or dangling dependencies.)
9. **Handle dead agents explicitly. A null result is recorded as failed ("agent died"), and a null verdict triggers re-verification, never a pass.** — Parallel calls can return null. (Silent nulls were nearly counted as successes.)
10. **If a run reports planned units missing, dispatch a completion agent for exactly those units.** — Re-running everything wastes the finished work. (This recovered two half-built features.)
11. **Never let two agents edit the same file at once. Tasks that share files run in sequence.** — Concurrent edits clobber. (File-conflict safety is the bound on parallelism.)
12. **When parallel agents must share files (registries, design-system files), each re-reads the file immediately before editing and makes minimal changes. Serialise expensive shared resources such as a render queue.** — Stale reads overwrite peers. (Parallel content agents overwrote each other's root-file edits.)
13. **Tell agents which paths another process is editing right now, and forbid them from touching those paths.** — Concurrent sessions collide. (Two sessions edited the same CI files.)
14. **Do not fan out many agents that each run browser-mode test suites. Let agents run typecheck and build, and do one serial test sweep yourself.** — Parallel browser suites saturate the machine and wedge the runner. (Load hit 10 to 16 and the runner hung for over 25 minutes.)
15. **Build in parallel but release serially. The version and changelog are singletons: each release re-reads the current version fresh, and parallel work ends in one integrated release.** — Concurrent releases tangle. (Two releasing workflows tangled the version bump, and one lost its issue-closing trailer.)
16. **Tell in-run agents "don't stop or ask: decide yourself" by ranking real alternatives and letting evidence win. Human questions belong in pre-flight and at the final yes.** — Background runs stall on questions nobody is watching. (Several runs sat idle waiting for an answer.)
17. **Agents that run long e2e suites run them in the foreground with a long explicit timeout and commit in the same turn. The orchestrator checks git status after every workflow and finishes any stalled release.** — Backgrounded tests end the agent's turn. (Verified-but-uncommitted work was left in the tree twice.)
18. **Return structured run data (diagnosis, plan path, per-task results with attempts and unfinished work, gates, docs) from every workflow.** — The orchestrator can then report and audit without re-reading transcripts. (Structured returns made the tier experiments possible.)
19. **Make bots loop-safe: skip events the bot itself authored, mutate only labels and comments (never the body that triggers "edited"), and serialise jobs that write shared state.** — A bot's own writes re-trigger it. (Triage label writes would have re-fired triage.)
20. **Know the platform's event semantics. On GitHub, a label change emits "labeled", not "edited".** — Triggers that listen for the wrong event never fire. (A backlog pass depended on adding labels to re-trigger triage.)
21. **AI steps in automation fail soft. On a missing key, an API error or a refusal, leave the item in a "pending" state that a deterministic job lists for a human.** — A red run loses the item, while a pending item gets seen. (A failed classification stayed visible on the queue comment.)
22. **Validate the shape of AI output even when the API promises structured output, and expect vendor endpoints to die silently.** — Vendors change and break without notice. (A hosted inference service began answering every request with HTTP 200 and the text "OK".)
23. **Keep ranking and closing deterministic: sort by the labels the AI applied, break ties oldest first, and upsert one sticky comment found by an HTML marker. Confine AI to one classification step.** — Deterministic jobs are testable, cheap and cannot hallucinate. (The queue job has no AI in it.)
24. **When re-classifying, clear the earlier mutually exclusive labels first.** — Otherwise values accumulate instead of being replaced. (An issue ended up with two priority labels.)
25. **Map a portable skill's canonical role names to the repo's real label strings in one table that the skill reads.** — Hardcoded labels break in each new repo. (The skill's "needs-triage" is this repo's "triage-pending".)
26. **Return a COMPACT result from a run: status, root cause, a gates table, the commit list, the merged findings by severity and the follow-up issues to file. Keep large per-stage outputs in the run journal and the spec and plan files, referenced by path, and cap the returned text (about 20 KB).** — A return value nobody can read is no return value. (In the first dogfood run the return was about 240 KB, and the orchestrator had to dig through the journal instead.)

## 7. Build (BD)

1. **Builder rule: execute the plan's task exactly, tick its checkboxes, run its tests and commit only your own files. If the plan's code does not compile against reality, fix it to match and REPORT the deviation. Report the commands you ran and their real output.** — Builders otherwise either redesign freely or blindly apply broken code. (This middle rule was the one that worked.)
2. **Put "only do the task you are given; do not invent additional work" in every prompt.** — Agents expand scope into refactors that break other slices. (Adjacent refactors collided with parallel work.)
3. **Request validators that strip unknown fields silently drop new ones. When adding a field, grep every write path and every validator.** — Fixing only the endpoint you were working on misses the rest. (A quick-create endpoint discarded two new columns for weeks, and elsewhere a stripped field meant a feature could never fire.)
4. **When a refactor removes a trigger, wire its replacement explicitly and test the downstream effect.** — An orphaned side effect fails silently. (A backup endpoint returned 404 forever, and "Last sync: Never" was literally true.)
5. **Never gate a warning indicator on a field that a cache can fill.** — The cache hides exactly the state the indicator exists to show. (A "lost data" chip never rendered because the local cache always supplied the name.)
6. **When you add an export to a module that tests mock, update every mock of that module across all test files.** — Mocks that lack the export break. (One new function broke nine test files.)
7. **When a page or component is reused across records (route param changes, no remount), re-read every derived or decrypted field on change.** — Otherwise the previous record's data leaks into the next one. (Navigating between two records kept showing the first record's name and ID.)
8. **Give every `void promise.then(...)` chain a rejection handler.** — Without one, cleanup and delivery silently never run. (Four recorders left an empty box after a dropped socket.)
9. **Check route registration order. A parameterised route registered first swallows later literal routes.** — The literal never matches. (`DELETE /:id` caught `DELETE /pending-reconciliation` and returned a 500.)
10. **In reactive UIs, an effect that fires on a state edge and re-arms on a transient state can loop forever. Use a once-per-episode latch that re-arms only on a genuine completion event.** — The loop can hang a whole test file. (An auto-reauth effect fired on every overlay show/hide edge.)
11. **A feature that silently skips when any config piece is missing ("not_configured") will be off in production without anyone noticing. Fail loudly, or surface the state in a health view.** — Silent degradation goes unseen. (Feedback image upload was off in production because one of four config values was missing.)
12. **Detect formats (dates, numbers, times) from the column's actual values. Never hardcode a format in a mapping recipe.** — Source templates drift. (A recipe hardcoded DD/MM/YYYY while the source used D-MMM-YYYY, which nulled every date.)
13. **Pin the validated model id in code and in every environment, list the known-bad ids, and keep a real-API check.** — A public model id is not necessarily usable on your account, and tests inherit the default. (An agent defaulted to a model that returned empty on the account, and staging was pinned to it too.)
14. **Make sure fixes actually reach clients.** — Stale cached code brings fixed errors back. (A service worker serving old code kept resurfacing errors that were already fixed.)
15. **Prefer zero new dependencies. If one seems necessary, stop and note it. When it is allowed, pin the exact version and install it in the worktree.** — Dependencies break builds. (A broken npm publish of a candidate package would have broken the build.)
16. **Split automation into pure, unit-tested decision logic and a thin I/O runner.** — That split is what makes self-checks possible. (The housekeeping logic module has no I/O at all.)
17. **Give each re-appliable definition (a database function, a view, a config block) exactly one file holding its current form. Keep immutable history for schema and data changes only.** — Otherwise "what does it do today?" means hunting for the last redefinition. (29 functions were defined more than once, and each small change restated about 117 lines.)
18. **If you disable an up-front validation (such as create-time body checks), require a test that exercises each new item.** — The failure moves to first use. (With function body checks off during apply, a typo fails only when the function is first called.)
19. **When several configs must agree (proxy routes, dev proxy, edge config), keep ONE list, generate the rest from it, and guard new entries the moment they exist.** — Hand-synced lists drift. (One API route was missing from staging's allowlist for three months.)
20. **Put each business rule (such as "what counts") in one place, a view or a function, with a static guard that fails when a query restates it.** — Inline recomputations drift from the canonical rule. (Several queries recomputed the counting rule inline and drifted from it.)
21. **A builder commits its plan checkbox ticks in the same commit as its task (or the plan does not use checkboxes). Verifiers ignore uncommitted plan ticks.** — Uncommitted ticks dirty the tree and show up in every verifier report as noise. (In the first dogfood run builders ticked boxes without committing them, and every verifier flagged it.)

## 8. Verify (VF)

1. **Verify each task with a FRESH, independent, adversarial agent as soon as it finishes, checked against an explicit authority order (mockup > spec > plan). Tell it: "you did not write this; assume it is wrong until your own commands prove otherwise; never trust the implementer's report; fix nothing; if unsure, fail."** — Implementers' self-reports are optimistic. (Per-task verifiers caught real traps that the builders had reported as done.)
2. **Verifier checklist: the files changed as described; the named tests exist AND pass when run; typecheck and lint are clean; a commit with the required trailers exists; there is no TODO, FIXME or "not implemented"; plan checkboxes are ticked; law checks pass by grep; scope is limited to the task's files; the reported symptom is resolved.** — Each item exists because a verifier once missed that class of defect. (The list grew one escape at a time.)
3. **Prove the regression test can fail. Stash or revert the fix (or plant a bad input), watch the test go red, then restore. Assertions must fail on the bad outcome, not merely "not throw", and the component under test must not be mocked.** — A test that passes on old and new code alike proves nothing. (A negative control caught a grouping test that passed with items in the wrong groups.)
4. **Verdict schema: passed, checks[{check, ok, detail}], unfinished_work (precise, naming files and symbols), code_defect (true only for real logic defects, not bookkeeping), summary. Feed unfinished_work verbatim into the repair prompt.** — Separating logic defects from bookkeeping makes the repair-rate metric meaningful. (Missing trailers had been inflating the defect count.)
5. **Repair loop: up to 3 repair and re-verify rounds per task. Repair runs one model tier UP from build, with the prompt "a previous attempt was rejected; fix exactly this".** — The task already failed once on the cheaper model. (Repairing on the same tier repeated the same mistake.)
6. **Never cheapen the verifier, and have it check claims in docs as well as code.** — Verification is the safety net for every cheaper stage. (The verifier caught a "+1 more" counting trap and two false claims in documentation.)
7. **UI acceptance drives the real page: seed the user's data shape, click the real control, assert the rendered DOM. Every UI state must render something visible. Nothing is fixed until the reporter confirms it in production.** — Logic tests do not cover what the page shows. (Two dedup fixes had green gates, yet production showed a blank section after the button was clicked.)
8. **Use the reporter's REAL data shape (anonymised) as the acceptance test and reason explicitly about those rows.** — A fix that passes tests but fails on the reported rows has failed. (Idealised fixtures hid the very bug that was reported.)
9. **When test doubles (virtual authenticators, mocked SDKs) cannot reproduce a real-device or real-vendor bug, say the fix is pending real-device verification.** — Do not declare it done. (A passkey fix could be confirmed only on the operator's phone.)
10. **Re-run the gates yourself, independently of the run, after a workflow reports green, and check the tree. Never trust subagent claims.** — Subagents misreport. (A re-run found nine broken test files, and a ship agent reported "zero commits" that actually existed. In the first dogfood run the independent re-run matched, which is what made the green believable.)
11. **Re-read and re-triage every finding a verifier labels "non-blocking", by severity, starting with defects and test gaps. "Non-blocking" is the verifier's opinion, not a verdict.** — Several are real defects. (A 500 where a 400 belonged, an empty input reaching a payment provider as an opaque 502, and a silent fail-open were all filed as non-blocking. In the first dogfood run the re-read found 4 real defects.)
12. **Verify a gate in both directions: it does not leak onto routes it should not cover, AND it covers every route it should.** — Most checks only test one direction. (A paywall check proved there was no leak but missed an ungated import endpoint.)
13. **Before release, cross-check the plan's unit list against the tree. A planned unit with no implementation is a STOP.** — Half-features otherwise ship. (A hardcoded unit list dropped units the plan defined.)
14. **Hold up as the standard a release agent that refuses to ship docs describing behaviour that cannot fire, even when the gates are green.** — Green gates can still hide dead features. (A validator stripped the field a feature needed, and the release agent blocked it.)
15. **After any background or multi-agent run, run `git status` and `git ls-files -d` before staging. Restore unexpected deletions without touching new work, re-run the gates, and commit explicit paths.** — Runtimes can delete files. (A checkpoint teardown deleted 259 tracked files, and `git add -A` would have committed the deletions.)
16. **Confirm a production deploy against the actual app's health/version endpoint plus the deploy log, never against a sibling site.** — A sibling site may embed the version from the main branch. (A marketing site showed the new version before production had deployed anything.)
17. **After a deploy, probe the new route itself, expecting its real status and content type, not just /health.** — The health endpoint can flip before the proxy reloads. (Production was misreported as broken during the reload window.)
18. **Prove data scripts idempotent: re-run in dry mode right after the real run and expect zero writes. On synthetic data, run a deterministic double pass: the second pass creates nothing, yet a genuine second record still lands.** — This catches dedup bugs in both directions. (A production backfill re-run reported "0 waived, 10 already had one".)
19. **When generated values depend on the environment (redirect or base URLs), check that the link points at a host the user can reach before handing it over. Use a dedicated test account so verification does not consume their one-time tokens.** — Bad links waste the user's time. (Sign-in links pointed to localhost, and a remote user tried three browsers over 15 minutes.)
20. **Declare an experiment's keep rule up front, discard changes whose measured gain is below the bar, and close the issue on measurement rather than opinion.** — Without a bar, every tweak looks worth keeping. (A voice bench discarded four tweaks that gained 2 to 4 points against a 5-point bar.)
21. **Build a discrepancy detector that compares your computed totals with the totals the source states about itself.** — It catches both over- and under-counting. (It flagged both a 356 and a 0 when the truth was 105.)
22. **For a race fix, write a race test that fails reliably before the fix and passes repeatedly after it, with no retries.** — One green run proves nothing for a race. (A navigation race test failed 3/3 before the fix and passed 30/30 across three runs after.)
23. **For UI issues, take screenshots at both mobile and desktop widths, before and after the change.** — Bugs are often viewport-specific. (A name header showed on desktop but not on mobile.)
24. **Check that the feature is reachable from the UI.** — A page with no link, or a blocked route, is of no use. (A built profile page had no link and collided with an API path.)
25. **Encode domain invariants as checks the verifier can grep for (forbidden user-facing vocabulary, destructive DDL, new unique constraints, secrets in output, raw colours instead of tokens), and back them with guard tests.** — Invariants that exist only in prose get broken. (Grep-checked invariants were reliably held.)
26. **Self-test the checker: plant known defects and confirm the review tooling surfaces them before trusting it.** — Unchecked checkers miss things. (A frame-review tool had never been tested on short-lived or duplicated elements.)
27. **Verify diagrams and visual docs by rendering them in a real browser: the diagram renders, labels meet a minimum size, and dialogs open, close on Escape and return focus.** — Syntax errors and unreadable labels only show up when rendered. (Broken diagrams had passed text checks.)
28. **Have a domain expert validate domain content.** — The builder is not the validator outside their own field. (A procedure list for another specialty was structurally fine but needed review from that field.)
29. **Remember that long-lived cache headers also apply to 404 fallbacks. Verify assets at the origin first, and avoid immutable caching on paths that may be requested before they exist.** — An early probe can cache "not found" for a year. (A brand asset URL served a cached 404 long after the file went live.)
30. **Remember that "tests passed" is not "deploy works": keep build, migrate and health-check failures aborting on the host even after a CI gate exists.** — Environment-level failures need their own checks. (A green stamp covers only the tested code.)
31. **Merge and dedupe every verifier's findings into ONE list, and make verifiers tag each finding with a severity: defect, test-gap, doc-copy, follow-up or bookkeeping. The summary lists defects and test gaps first, and the post-run re-read works from this list.** — Scattered per-verifier lists bury real defects under repeated bookkeeping. (In the first dogfood run about ten verifiers each returned their own list with heavy duplication, and a page stuck on Loading, misleading copy and a raw 500 hid among notes about checkboxes.)

## 9. Tests and gates (TG)

1. **Run every gate layer (typecheck, lint/format, unit, e2e, build, doc checks) before every commit, and put the test counts in the commit message.** — Untested hot-patches cause regression cycles. ("You're not running tests before you're committing", after three or four cycles. Separately, a lint slip blocked a release.)
2. **Before calling a run green, save the FULL output to a file, grep all of it for "failed" and "flaky", and compare the passed count with the previous run. Never judge from the tail.** — Some runners print "N failed" above "N passed". (The tail said "119 passed" when 1 had failed, and a release was reported as "0 failed".)
3. **Tell your own command's exit code apart from the test result.** — A trailing grep that finds nothing exits 1, and `grep -c` printing 0 breaks `&&` chains. (An "exit 1" came from a final grep, not from a test.)
4. **After any edit, run the whole affected suite, not only the file you touched.** — Other tests depend on what you changed. (A guard edit broke three server tests elsewhere.)
5. **After merging two branches that were each green, re-run the full gates, e2e included, on the combined result.** — Combinations fail in new ways. (A merged release candidate showed server failures that neither branch had.)
6. **The gates agent runs the full gate list until it is green, fixing and committing as it goes, and reports a structured result: all_green, gates[{command, passed, output_tail}], failures_fixed, remaining_failures.** — A single "tests pass" claim hides which gate is red. (Mixed results were once reported as green.)
7. **Change a TEST only when it asserts behaviour the app deliberately no longer has, and cite the commit. Never skip, retry-wrap, raise timeouts, loosen assertions or weaken a guard to go green. If that seems necessary, stop and report.** — Pressure to go green tempts agents into cheating. (Agents tried to weaken detection guards to pass.)
8. **Keep a documented known-flaky SET. A failing set is non-blocking only if it matches the known set, and a new failure in the touched area blocks.** — "E2E is red, ignore it" hides regressions. (Comparing sets caught new failures that counting had hidden.)
9. **To diagnose red e2e specs, run each failing spec alone and in the full run. Passing alone but failing in the run means ordering or shared state, while failing alone means its own cause. Require green twice in a row.** — Red specs often have several distinct causes. (Ten red specs had three causes: a pool torn down per file, proxy routing and stale assertions.)
10. **Decide per issue whether e2e runs inside the workflow. If it needs shared resources (a DB, default ports) that another worktree is using, skip it there and run it from the main checkout at merge. Report "skipped" as skipped, never as passed.** — Worktrees often lack a DB and env. (Worktree builds reported suites "skipped by env".)
11. **Tell agents which failures in the shared environment are expected and not theirs to fix: they report them and change nothing.** — Agents otherwise "fix" other branches' problems. (A parallel branch's migration in the shared DB broke a test, and an agent tried to fix it.)
12. **When the test runner is unavailable, fall back to typecheck, build and a static diff review, rely on CI for the definitive run, and say that is what you did.** — Honest partial verification beats a false green. (A slice shipped this way while the runner was wedged.)
13. **Fresh-fixture e2e never reproduces legacy-data bugs. When a feature adds a field other code depends on, ship a backfill, defensive handling of the absent value, and a legacy-state fixture.** — Old rows lack the new field. (A null on pre-feature records broke every write on staging data.)
14. **Fixtures copy REAL formats (date strings, separators, totals rows, embedded sub-tables), satisfy real constraints and model the scenario they claim (three different people get three different identities). A dry run on a real, scrubbed file is the true gate for ingestion code.** — Idealised fixtures hide bugs. (A green gate hid a date bug that imported 0 of 105 real rows. A fixture's "three people" shared one identity.)
15. **Run DB-touching tests against a real database before calling them done.** — Mocks pass while the real DB rejects the operation through row-level security or constraints. (A pre-auth lookup passed on mocks but silently fell back against real Postgres.)
16. **Long tests that wait on external APIs while holding DB connections can exhaust the pool. Raise limits, close connections between tests, or serialise those specs.** — Pool exhaustion looks like random failure. (Eight specs failed with connection-ended errors.)
17. **CI must gate deploys on tests. If the platform cannot enforce a required check, put the gate in the deploy script: deploy only commits that CI stamped green with an immutable per-commit marker ref (e.g. `refs/ci-green/<sha>`), never a moving branch.** — Pipelines that skip tests depend on memory, and moving refs race. (Hosts deployed untested commits, and branch protection returned 403 on the plan in use.)
18. **Remember that a green badge does not prove the suite ran. Check that the job actually executed and reported counts, and make critical jobs required.** — Non-required jobs fail invisibly. (A missing secret file broke migrate, and because e2e was not required, CI went green while the suite never ran for a release.)
19. **Add a new suite to CI as non-required, and promote it to required after about 10 consecutive green runs.** — An unproven suite blocks every deploy with flakes. (E2E stayed non-required until it proved stable.)
20. **Give heavy jobs a timeout, treat a timeout as red, and shard large browser suites before they wedge.** — Wedged jobs leave results unreported. (443 browser test files wedged with 142 unreported, and two shards halved both time and load.)
21. **Use a condition like `if: !cancelled()` for checks that must always run, so an earlier red step cannot silently skip them.** — The default `success()` skips them. (A failing stub suite would have skipped the release smoke test.)
22. **If CI checks only run on pull requests and you commit straight to main, run those checks locally in every release gate.** — Otherwise CI is bypassed entirely. (Doc-quality CI fired only on PRs.)
23. **Turn each repeated slip into a guard test: version consistency, route-to-proxy allowlist, raw controls outside shared primitives, dev tooling imported into the app, retired identifiers, allowed public-form fields.** — Conventions drift, and a failing test is a fact. (Each of these slipped at least once. A version drifted for about 10 releases.)
24. **Remember that a shared component plus documentation is not enough. Add a guard that fails when a page re-implements the control.** — Documented conventions still drift. (7+ toggles were page-local. A colour rule was broken in 41 files outside a guard and in 0 inside it.)
25. **When a guard needs an allowlist of existing violations, make it shrink-only: any count change other than downward fails. Aim to delete the allowlist.** — The guard lands now and the debt ratchets to zero. (Several allowlists were emptied this way.)
26. **Make exemption lists self-cleaning: an exemption that matches nothing fails the check.** — Stale exemptions rot into silent holes. (Render and query exemption lists fail on stale entries.)
27. **Give every generated file a `--check` mode that CI runs.** — Hand edits or forgotten regeneration then fail the build. (The ADR index, a data map and form options are all checked.)
28. **Automation that acts on shared state (closing issues, deploying) runs its own unit tests first and refuses to act if they fail.** — Broken logic must never mass-close issues. (The housekeeping job self-checks before it acts.)
29. **Give checks that depend on history or tags a full fetch, and say explicitly what a shallow clone skips.** — Shallow clones silently skip. (The changelog and housekeeping checks use `fetch-depth: 0`.)
30. **When a branch push and a tag push hit the same commit, queue the CI runs instead of cancelling one.** — The cancelled run may be the one the release needs stamped. (Concurrency settings were changed to queue.)
31. **Lint deploy and shell scripts in CI (e.g. shellcheck).** — They are load-bearing and otherwise untested. (Deploy script bugs had reached hosts.)
32. **A gates stage that can commit fixes needs at least medium effort and a model that follows instructions reliably.** — It reads output and commits, so a careless model can damage the branch. (Gates looked mechanical but turned out to be risky.)
33. **If a concurrent session deploys without tests, treat staging and production as suspect and run the whole suite once things settle.** — State you did not create is untrusted. (A parallel terminal pushed fixes and a version bump straight to production, untested.)
34. **Profile discovery excludes checks that only run in a PR or CI context (they read PR metadata or CI-only variables). Record them as `ci_only` in the profile, never in the gate list.** — Run locally they fail every time, so a gate list that includes them is red for a reason unrelated to the change. (In the first dogfood run a PR-only docs check failed outside a PR, and the post-run audit caught it.)

## 10. Isolation and environment (IS)

1. **Build big features in a dedicated git worktree on its own branch, outside the main checkout. Every shell starts with `cd` to it, agents use its absolute path, and other active worktrees are named as off-limits.** — The shared checkout gets mangled. (A 78-minute run broke when a concurrent terminal advanced main and HEAD switched.)
2. **Prepare a fresh worktree: install dependencies, run any code generation or sync step, link the real gitignored secrets and source the main checkout's env file. Never create dummy secrets.** — Missing env looks exactly like a code bug. (A dummy secrets folder failed 22 photo specs, and "command not found" exit 127s came from a missing install.)
3. **Reserve the developer's default dev ports for them. Agents use assigned spare ports with strict-port flags and kill every server they started before finishing. Check what owns a port (`lsof`) before e2e, and kill only stray processes whose cwd is a finished worktree.** — Stray servers hijack the next run, and blind killing takes down the human's server. (A verifier refused a task four times because of a stray server running code 111 commits behind.)
4. **Isolated e2e runner: write a temporary config that rewrites the proxy target and test base URL to spare ports (dropping the runner's own webServer block), start the backend and frontend, wait for both health checks with a timeout, run, then always restore the patched files and delete the temporary config.** — Otherwise worktree e2e collides with, or silently uses, the developer's servers. (Several "isolated" runs had used the dev server.)
5. **Point every URL the tests generate (sign-in helper, magic-link and redirect base, app origin, WebAuthn origin and RP id) at THIS run's port.** — One forgotten default sends tests through someone else's server. (The sign-in helper defaulted to the shared dev port and tested old code.)
6. **Mirror the runner's configured server environment in isolated runs: test admin accounts, the insecure-cookie flag for http, local object storage.** — Removing the webServer block also removes the env it injected. (Admin-gated specs failed.)
7. **If the servers do not come up, abort loudly with the log tail and still clean up: kill pids and listeners, restore configs.** — Half-started runs leave debris. (A failed start left patched configs behind.)
8. **End every isolated run with a cleanup report: zero listeners on its ports, default ports untouched, and `git status` showing no tracked changes.** — Cleanup you have not proved keeps leaking. (Leaked servers recurred until the report existed.)
9. **Stop background workers that share the test database, or give tests their own DB and queue.** — Workers steal test jobs. (A dev worker with a real key grabbed e2e jobs, billing the API and failing tests.)
10. **When a missing optional service config (e.g. object storage) fails many specs at once, check the environment first.** — It is usually a false alarm about the code. (18 media specs failed and were briefly mistaken for a regression.)
11. **Worktrees sharing one local DB can show false migrate failures, so judge migrations on a clean, in-order database.** — Another branch may have changed the shared DB. (CI and production starting clean were unaffected.)
12. **Do not run a test suite while another agent rebuilds the same frontend.** — Concurrent builds cause spurious failures such as "failed to fetch dynamically imported module". (An isolated retry passed.)
13. **Keep large media and content production out of the product repo.** — Clones, CI, worktrees and agents stay fast. (4 GB of video moved to its own private repo.)
14. **Pin the CI runtime version to exactly what the hosts run, and bump the two together.** — Version skew makes a green CI meaningless. (CI and hosts drifted apart.)
15. **Make sure the test environment has the real capabilities the feature needs: codecs, fonts, hardware APIs.** — Bundled test browsers may lack them. (The bundled Linux browser had no H.264 encoder.)
16. **Throwaway worktrees (negative controls, bisects) do a real dependency install, such as a frozen-lockfile install. Never symlink dependencies from another checkout; link only the secrets and env.** — A symlinked dependency tree resolves modules from the other checkout, so module mocks break and the control fails for the wrong reason. (In the first dogfood run negative controls failed spuriously because the throwaway worktree's dependencies were symlinked from another checkout.)

## 11. Deploy and infrastructure (DP)

1. **Prefer pull-based deploys, where the host polls, over CI pushing over SSH. Make deploys idempotent (no change is a no-op), fail-safe, single-flight (a non-blocking lock) and logged phase by phase.** — Push deploys are fragile and need inbound credentials. (The host throttled CI runner IPs, and the pull model then had zero failures.)
2. **Build into a side directory and swap it in only after a successful restart. Never restart on a failed build or migration, and never overwrite runtime secrets or user data.** — A broken commit should fail to deploy, not take the running version down. (A broken release candidate failed its build, and production stayed healthy.)
3. **Order deploy steps so that anything which can abort runs before anything users can see.** — Otherwise an abort leaves "new frontend, old backend". (A backup step hit a quota after the frontend had already rebuilt.)
4. **Prune everything a deploy creates every time (snapshots, backups, artifacts), or rely on built-in retention.** — Quotas eventually block deploys. (One manual snapshot per deploy hit a 100-snapshot cap and stalled production.)
5. **Take a pre-migration database snapshot on production deploys.** — It makes a bad migration recoverable. (Paired with the pruning rule above.)
6. **Seed reference data as an idempotent deploy step next to migrations.** — Migrations create empty tables, and manual seeding gets forgotten in one environment. (Production shipped with an empty reference table.)
7. **Remember that a self-updating deploy runs the PREVIOUS release's copy of its own script. Script changes lag one release, so never rename or delete a file the old copy calls in the same release, and run a new step by hand on the release that introduces it.** — The old copy is what actually runs. (A new seeding step did not fire on its own release.)
8. **Use one deploy model for staging and production, differing only in the tracked ref, secrets and database. Production gets the mechanism that has already been proven.** — Two models double the debugging surface. (A separate production push model was abandoned.)
9. **Remember that a secret store is not the runtime: if the server reads files or env on the host, something has to materialise the secret there.** — Adding to the store does nothing on its own. (Production secrets sat in a parameter store that the server never read.)
10. **On a host that is a git clone, list the untracked runtime directories (env, secrets, uploads) and preserve them on any re-clone.** — A missing secret aborts migrations. (The staging host needed three untracked directories preserved.)
11. **Reload proxy or edge config only when it differs from the live copy, and provide a separate, surgical workflow for env changes when deploys exclude the env file.** — Needless reloads add risk. (Env changes could not ride a normal push.)
12. **Commit deploy scripts with the executable bit in git (`git update-index --chmod=+x`), and never chmod a tracked file on a pull-deploy host.** — The mode change dirties the tree, and the deploy guard then refuses every deploy. (A manual chmod blocked all deploys.)
13. **Know which sites deploy straight to production on every push to main.** — A push there is a production change. (The marketing and docs sites were not tag-gated like the app.)
14. **When an auto-deploy webhook does not fire, trigger the deploy through the provider's API or CLI and watch it until it reports success.** — Webhooks are unreliable. (A docs site repeatedly failed to rebuild on push.)
15. **Require a minimum soak time on staging before a tag may deploy to production.** — Problems surface with time. (Production required a tag to have been on staging for at least an hour.)

## 12. Git, merge and release (GR)

1. **Never run `git add -A`. Stage only the task's own files, and keep an explicit never-stage list for known stray untracked files.** — Strays get swept into unrelated commits. (A stray icon file kept appearing in commits.)
2. **When git reports `index.lock` while agents are committing, wait a few seconds and retry. Remove a lock only when it is stale (old, zero bytes, no git process running).** — Deleting a live lock risks corrupting the index, while a stale one silently blocks everything. (Both cases happened.)
3. **After merging a worktree agent's work, check the shared checkout's current branch and HEAD.** — Agents can leave it on their own branch. (Commits landed on a leftover fix branch while main stayed stale.)
4. **Require exact commit trailers (co-author and session link) and an issue tag in the subject in every agent prompt. After every workflow, audit every commit since launch for the trailer, and treat an unattributed commit as rogue until it is explained.** — Attribution is how rogue commits get detected. (A small model committed to main under the human's name with no trailer.)
5. **Bump the version only through the one script that rewrites every place it lives, and add a CI check that each of those places matches the VERSION file.** — Hand edits leave copies stale. (The app showed 0.15.88 while VERSION said 0.15.98, for about 10 releases.)
6. **Tag every release with an annotated tag on the bump commit, even before production exists. Never delete published tags, and fix forward with a new version.** — Tags are the history. (A tag was skipped because "tags are for production".)
7. **Run release steps under `set -e`, or as one `&&` chain that includes the tag and the push.** — Otherwise a failed check does not stop the tag. (A changelog check failed and skipped the bump, but the tag and push still ran.)
8. **After any merge, check that changelog entries still sit under "Unreleased", and add a CI check that each released section reads exactly as it did at its tag. Prove the check with a planted misfile.** — Git files Unreleased entries into released sections. (This happened six times, and one release was tagged without a bump.)
9. **Do version bumps, changelog finalisation and the final commit in the main loop after a workflow returns, never inside the workflow.** — Workflows run on stale bases and can be torn down. (Concurrent bumps conflicted.)
10. **Close issues when work reaches production, not when it merges. A plain `(#NN)` never closes anything, and if main deploys to staging, do not use `Closes #NN`. Use a trailer such as `Ships: #NN` that a job processes on a CI-green release tag.** — Platform keywords close issues on merge, before production. (Six shipped issues stayed open, and `Closes` would have closed them early.)
11. **Do not let a newer red tag hide an older green one: ship and close from the newest GREEN tag, and say which newer tag is pending.** — The closing rule should mirror the production gate exactly. (This avoided closing issues whose code was not live.)
12. **Select release tags with a strict regex (`^v\d+\.\d+\.\d+$`), sort them numerically, peel annotated tags to their commit, and fetch with `--prune-tags`.** — String order ranks v0.17.5 above v0.17.10, and globs match rc tags. (A deleted rc tag lingered on a host, sorted above the release and was auto-deployed.)
13. **When production deploys from tags, run data scripts that depend on new schema AFTER the tag deploys. A backfill that runs before re-applied definitions sees the OLD definitions, so it must inline any new logic. Plan for the window between the new rule going live and the backfill landing, and have the backfill ready before tagging.** — The schema does not exist in production until the tag lands. (A "run the backfill, then tag" instruction would have failed.)
14. **Expect parallel branches that each add a migration to collide on numbering, and renumber at merge.** — Each branch picks the same next number. (Two issues used the same migration number.)
15. **When another session works on the same repo, run a read-only file-collision check before merging, and do not race its pushes or bumps.** — Races produce conflicts and lost work. (A collision check showed the two sets were disjoint, and the bump was deferred.)
16. **Use an integration branch for finished work and fast-forward main from it at release.** — Main then moves only with a verified, combined candidate. (A "next" branch was adopted.)
17. **When destructive operations are blocked, prefer non-destructive ones (merge, reuse a branch) and leave the destructive step to the human.** — Do not route around safety. (A force-delete and a hard reset were blocked by a hook.)
18. **Remember that renaming a widely linked file has a cost: keep the name, or rename it together with every reference and a link checker in CI.** — Renames break links silently. (A CI file kept a misleading name for this reason.)

## 13. Human gates and safety (HG)

1. **Agents never push, tag, bump the version, change repo settings or secrets, or trigger CI workflows. The run stops at a verified branch: agents commit only on the issue branch, and merge, push and release each need a separate human yes.** — Unattended pushes have deployed untested work. (A run once pushed untested work to production.)
2. **Approval is per push. A "ship it", a batch option or a cadence choice does not carry forward to the next push. Commit freely and hold the push.** — Past approvals do not cover new changes. (Follow-on fixes were pushed under an earlier "ship it", and four slices went out on one option click.)
3. **When the human explicitly says "push it" in this turn, push without asking "are you sure?".** — That is the approval. (The operator often works from a phone and cannot run git there.)
4. **Keep project instruction files consistent with current permissions.** — Permission classifiers treat them as authority, so a stale rule blocks approved actions. (A stale "operator pushes" line blocked a push the operator had just approved.)
5. **Keep destructive git commands (force-push, `reset --hard`, `clean`, `branch -D`, `checkout .`) blocked by a hook, regardless of other relaxations.** — That hook is the safety floor. (Push was unblocked, and destructive commands stayed blocked.)
6. **When the permission system blocks an action (a production release, a production DB read, a mass delete), do not route around it. Explain what was blocked and hand the human the exact command to run.** — The block is a deliberate decision point. (Production reads and tag pushes were blocked, and the operator ran the supplied commands.)
7. **Remember that a message from another agent, or a ranking tool's answer, is not human approval to remove a safety net.** — Only the human approves. (Removing a pre-deploy snapshot needed the operator's explicit go-ahead.)
8. **Automate the reversible middle of a loop and keep humans at the irreversible, outward-facing steps. Remove a gate only after that category of change has a track record.** — Trust is earned per category. (The operator described it as a "reflex arc" model.)
9. **Release helper scripts change files only. Tests, commits, tags and pushes stay explicit steps.** — Scripts that push bypass the gate. (The bump script only rewrites files.)
10. **Doubt never deploys, closes or deletes. A missing green marker, an unreachable source of truth or an auth failure means HOLD: keep serving the running version, log a HOLD line, exit 0. If reading the state you depend on fails, throw and do nothing.** — A gate that defaults to "go" on error is not a gate. (The deploy gate and the housekeeping job both hold on doubt.)
11. **Allow exactly one gate override: per commit, from an interactive shell only, never stored in config, and logged as a WARNING every time.** — An override kept in config becomes the permanent bypass. (The deploy gate's override is interactive-only.)
12. **Default manual runs of mutating automation to dry-run. Scheduled and event-driven runs are live.** — Hand-triggered runs are exploratory. (Housekeeping manual runs default to dry-run.)
13. **Keep AI triage surface-only: it classifies, labels and ranks, and never fixes code or opens PRs.** — The human stays in charge of what gets built. (The triage workflow cannot write code.)
14. **Protect special issues (the pinned queue, anything labelled keep-open) from automated closing.** — Automation will otherwise close them. (The queue issue is always exempt.)
15. **Make "nuke data" operations an operator-only, scoped, transactional script (correct FK order, idempotent, reports counts), never a consumer button.** — A wipe button is a foot-gun. (It would have endangered the owner's demo data, and hand-written SQL kept leaving orphans.)
16. **With account-wide tool access, touch only the resources of the project in scope unless explicitly asked.** — Integrations can reach unrelated business resources. (One connector could modify unrelated DNS.)
17. **Make deploy changes fail safe: red, pending or missing CI keeps the current version running and logs loudly, with a documented override.** — Failing open deploys untested code. (Hosts had been deploying untested commits.)
18. **Honour any stricter gate the human declares for a campaign, such as a yes before each commit, on top of the defaults.** — The human sets the floor, never the agent. (In a long refactor campaign the operator asked for a summary, then a yes to commit, then a separate yes to push, for every item.)

## 14. Privacy and security (PS)

1. **Never write sensitive identifiers (names, record numbers, birth dates, customer PII) into issues, commits, PRs, docs or fixtures, even in a private repo. Refer to records by opaque id prefix, date and type, keep screenshots local, and have the verifier check.** — The code host is not a sensitive-data processor. (Real identifiers copied from screenshots reached tracker issues, and a triage bot forwards issue bodies to a model.)
2. **Treat the issue tracker as an external processor and scan text for identifiers before creating or commenting.** — Bots and integrations forward its content to vendors. (Triage sent every issue body to an outside model.)
3. **Remember that scrubbing current files does not scrub git history. Plan a history rewrite before a repo goes public, and add a guard so nothing new gets in.** — History is public once the repo is. (Old commits still held identifiers after the tree was cleaned.)
4. **Guard against retired sensitive tokens by storing only their hashes in a test that hashes every word of every tracked text file. Use obviously synthetic fixture names.** — A plain-text deny-list would itself re-leak the tokens. (Identifier tokens were scrubbed and guarded this way.)
5. **Give agents no production access: no querying production or staging databases, no reading production logs. They reproduce locally and list any production-only fact as an open question.** — Sensitive data must never enter agent context. (Local reproduction was always possible, or the gap was made explicit.)
6. **Acceptance harnesses that must touch real sensitive data print only aggregate numbers, with an assertion that throws if anything row- or identifier-shaped reaches the output. Analyse sensitive files through a scrubbed dump. Agents read the numbers, never the file.** — Real-file dry runs are the true gate, but agents must not see raw records. (The green dry-run script works this way.)
7. **Classify data into storage classes up front. Keep sensitive media only with providers that hold the required compliance agreement, and re-read that boundary before any storage decision.** — The boundary gets forgotten in brainstorming. (A media spec targeted the wrong provider.)
8. **Never trade a core privacy guarantee for a fixable UX problem. Solve the UX in the client or the flow.** — Guarantees cannot be taken back. (Storing a password hash server-side was rejected, and routing fixed the UX instead.)
9. **Before anything sensitive reaches a model, strip it with one mechanism, verify independently with a different mechanism, and block the send if anything remains.** — One layer will miss something. (Two-layer de-identification is a hard precondition for model calls.)
10. **Keep the most sensitive values (money, keys) out of AI calls entirely and handle them with deterministic code.** — There is nothing to leak if they never go in. (Financial amounts are never sent to the model.)
11. **Before adopting a vendor's agent or hosted product for sensitive data, check its data retention and compliance eligibility.** — A stateless API call may qualify where an agent product does not. (A hosted agent product was ruled out on retention grounds.)
12. **Put third-party analytics only on public surfaces. In a shared build, gate the snippet by build environment and grep the sensitive app's build output for zero references.** — Shared builds leak snippets. (Docs and app shared one build.)
13. **Check an ML model's licence before adopting it, and validate it on your real input domain.** — Licences and training domains disqualify models. (One PII model was non-commercial, and another was trained on native scripts while the inputs were romanised names.)
14. **Make access gating cover per-deploy preview URLs (wildcards), and give access apps at least one allow policy.** — Each preview has its own public URL, and zero policies silently sends no login code. (Previews were public until a wildcard was gated.)
15. **Hide admin routes from non-admins with 404, not 403, on both frontend and backend.** — A 403 advertises that the route exists. (The operator console is hidden this way.)
16. **Use secrets without printing them: read them from a file straight into the command's environment. CI secrets are throwaway, generated per run with restrictive permissions, and only the one step that needs a real key gets it. Production keys never sit on the dev machine; the human applies them through the server's secret store.** — Printed or copied secrets leak. (A scoped deploy token is used inline from a mode-400 file, and the agent declined to hold a production key.)
17. **Check which identity a connector is signed in as before sending or drafting on someone's behalf. Write drafts only, and let the human send.** — The wrong account means the wrong organisation. (Drafts were twice created in the wrong mailbox.)
18. **Give feedback attachments a required "no sensitive data" acknowledgement, a private bucket with expiring links, and the same redaction library the main flow uses.** — Reuse the gate instead of reinventing it. (The feedback channel reuses the existing redaction.)
19. **Keep development-time tools that call third-party services unreachable from shipped code, enforced by a test that fails if app source imports them.** — The app must gain no data-flow or contractual dependency on them. (The ranking helper is guarded out of app code.)
20. **Declare least-privilege permissions per CI job.** — Broad defaults grant too much. (Triage jobs get `issues: write` only.)
21. **Mark API responses that carry private data `no-store, private`, and pin the fix with a regression test that covers error responses too.** — Browsers cache authenticated JSON. (A top-level navigation served a cached authenticated response.)
22. **When a page and its data share one URL distinguished by headers, set `Vary` and no-cache on app pages.** — Otherwise the browser can serve a cached page where data was requested. (The no-cache rule matched only `/index.html`.)
23. **In a triage rubric for a sensitive-data app, round anything touching data integrity or confidentiality UP to top priority, and round pure polish down.** — Automated triage otherwise under-rates exposure bugs. (The rubric has an explicit tie-break.)
24. **Upload test traces and screenshots only on failure, only from synthetic accounts, before any step that touches real data, and with short retention.** — Traces capture whatever the test touched. (A trace policy was added to CI.)
25. **Fail closed on capability signals: while status is pending or errored, treat an optional feature as unavailable. Status endpoints return only a boolean, never key material or its length.** — Client prefs alone can expose an unconfigured feature. (A cloud voice toggle rendered before the server key existed.)
26. **Make a test stub or bypass guard fail closed: allow it only on an explicit opt-in value, never on a value that is also the default when the variable is unset.** — An unset variable must not enable the stub. (The guard allowed the stub on "development", which was also the unset default, so production could have accepted it.)

## 15. Data integrity (DI)

1. **Normalise human-typed identifiers (emails, IDs) at both write and read (lowercase, trim, strip leading zeros) and index the normalised form.** — Exact-match lookups on typed input are traps. (Byte-exact emails and leading-zero IDs both caused silent no-matches.)
2. **Never regenerate a root key or identifier that existing data depends on. Create it once, keep a canonical master copy, re-wrap rather than regenerate on credential change, and make resets keep primary records.** — Regeneration orphans data. (A second device generated a new key, and every imported record became unreadable there.)
3. **Never let a client push its own state over a canonical master that already exists. Probe for the master before creating anything, on every entry path, shortcut flows included.** — Shortcut paths skip the probe. (A biometric-first onboarding path overwrote the master key.)
4. **On unlock or sync, detect a mismatch between local state and the master and force a resync. Never silently show blanks.** — Silent blanks look like data loss. (A device holding an old key showed blank names with no warning.)
5. **Recover diverged clients from the client that still holds a full plaintext cache: export a safety copy, promote it to master, re-encrypt everything, then restore the other clients from the master.** — This recovers data without wiping it. (The operator's records were recovered this way.)
6. **Where an inconsistency can be fixed from data the client already holds, self-heal silently on load.** — The error state then only ever means true data loss. (Undecryptable records were re-encrypted from the cache.)
7. **Remember that missing is never zero. Compute every rate only over records that have the value. Fill from a labelled estimate ladder or exclude, hide the metric if nothing qualifies, always show coverage ("N of M"), and keep estimates out of precise comparisons.** — Zeros fabricate results. (Untimed records produced an impossible 0.2 hours per case.)
8. **For messy real-world data, prefer completeness over strict dedup. Use soft, review-gated detection plus import-time prevention, not hard unique constraints, and document why.** — Legitimate look-alikes exist. (Same-day double procedures, bilateral records and corrected IDs would all be rejected by a hard constraint.)
9. **Make imports idempotent on a stable key. On a match, fill only the missing fields and never overwrite a populated field with a different value. Surface any conflict for review.** — A conflict is a red flag, not an update. (A conflicting name on one ID turned out to be an ID typo shared by two different people.)
10. **Decide the authoritative source for each field separately. Never blend sources, never auto-overwrite contested fields, and never auto-delete local records the other source lacks: flag them.** — Different sources own different truths. (Billing sheets own identity, while the user owns clinical content.)
11. **Make caches evictable: reconcile down to the authoritative set only on a full sync (never on a partial page, offline, or by dropping pending writes), and make a delete at the source also delete from the cache.** — Caches that only grow lie about counts. (A local name cache showed 799 entries for a much smaller real record count.)
12. **Use one write path: write to the authoritative server first, then update the cache on success.** — Two write paths race. (A single server-first path removed a two-store race.)
13. **Map imported columns by header name, never by position. Detect where the header row really is, and normalise header text.** — Layouts move. (Columns moved and were renamed between months within one workbook.)
14. **Use fingerprints only as lookup hints, never as trust gates. The reconciliation maths decides which recipe works.** — Sources re-model their layouts. (A source's financial layout changed every year.)
15. **Detect partial periods (e.g. 9 of 12 months) and label them on every display of that period, not only the currently selected one.** — Unlabelled partial data misleads. (A partial-year marker vanished whenever its chip was not selected.)
16. **Check that default statuses match the users' real flow. Records created from an authoritative source should be born verified.** — A wrong default makes a shipped feature look missing. (105 imported records looked unverified.)
17. **Store a learned artifact as a declarative recipe applied by a small interpreter, never as generated executable code.** — Recipes are safe, reviewable, versionable and shareable. (Generated code was rejected for its security surface.)
18. **Run reconciliation in both directions, since the two directions mean opposite things. Scope it to the window the source covers, and word results as "possible" with a "review" action, never as an accusation.** — A missing record could mean unbilled work, or an incomplete log. (This was the unbilled-case detection design.)
19. **Dedupe reference entities as part of any dedup effort.** — Duplicates poison anything hashed or keyed on them. (Several records for one institution made an identity hash untrustworthy.)
20. *Moved to `references/packs/data-import.md`: currencies.*
21. *Moved to `references/packs/data-import.md`: benchmark provenance.*
22. *Moved to `references/packs/data-import.md`: crowdsourced reference lists.*
23. **Remember that soft deletes leave orphans that block hard deletes. A real reset walks the live FK graph children-first in one routine.** — Hand-written deletes miss edges. (Soft-deleted records left pinned rows, and non-cascading FKs blocked deletes.)
24. **When deciding whether to re-apply something, check for divergence between a fresh CI environment and long-lived production.** — Skip-if-unchanged can be right in CI and wrong in production. (A cascading DROP could remove a function production would then skip re-creating. The fix was "checksum changed OR any migration ran".)
25. **Keep migrations that auto-run on production additive only (create, add column, create-or-replace), and have verifiers grep for drop, truncate and delete.** — They ship with the tag and cannot be taken back. (This is a standing verifier law.)

## 16. Design and UX (UX)

1. **Treat errors that appear in normal use as instability. Remove their root causes, never hide, swallow or restyle them. List every error surface, classify each (reachable bug / recoverable but mishandled / genuinely exceptional), fix the first two kinds, and keep the third. Verification rejects paper-overs.** — A restyled error is still a bug. (A "calm messaging" recolour was proposed for self-inflicted bugs and emphatically rejected.)
2. **Never let an error message lie: show "couldn't reach the server" only for a real network failure.** — Lying errors send users and debuggers the wrong way. (Network errors were shown for non-network failures.)
3. **Change WHEN an alarm is raised separately from WHETHER an unsafe action is blocked. Transient errors still fail closed but must not trip sticky global states, and sticky flags need a self-heal path.** — A single blip can strand users. (One transient network failure trapped users on a recovery modal.)
4. **Never leave the UI blank: after any action, a section renders exactly one visible outcome (results, an explicit "none", or a readable error). Contain failures to the failing section, and test each state.** — Blank looks like broken. (Two production bugs blanked a section and a whole page.)

UX-5 to UX-35 are in `references/packs/ux.md`.

## 17. Docs (DC)

1. **Make a documentation-impact decision for every change. The PR states either "docs updated" or "no docs needed" plus a real justification, and CI enforces exactly one choice and a minimum length.** — Without enforcement, docs lag behaviour. (A PR missing the section counts as incomplete.)
2. **Count user docs as part of done for any user-facing change: keep the content current, not just the version stamp, write in plain language, and state privacy guarantees accurately. A changelog entry does not count.** — User guides go stale while changelogs move. (A version bump left docs describing flows that no longer existed.)
3. **Never let docs promise what the code does not do. Check every sentence against the code, have the changelog claim only what shipped, and never claim production is fixed unless the deploy path really ships the change.** — False docs cost trust. (A note claimed a removed item "can be restored" when no such path existed.)
4. **Docs stage scope: user docs where behaviour changed, developer docs for the changed code, the glossary only if a term is resolved, and the changelog under "## Unreleased" (never the version file). Then rebuild the docs, rerun the doc checks, and index new specs.** — Docs drift when they are not part of the run. (They drifted every slice before this rule.)
5. **Write specs, plans and ADRs to predictable repo paths, and link each from an index page in the same change.** — Unlinked docs get lost. (Specs written to scratch vanished between sessions, and unindexed specs failed the checks.)
6. **Add an ADR only when the decision is hard to reverse, surprising, and a real trade-off. Ground it in cited evidence and never invent rationale.** — ADR sprawl and fabricated reasons devalue the record. (Both appeared in early doc passes.)
7. **Record rankings, the decision and any overrules inside the ADR, and decide whether to amend or create a new one.** — Future readers see why, not just what. (ADRs carry option-probability tables.)
8. **Number ADRs sequentially without backfilling gaps, give each exactly one owning overview page, and generate the index with a CI check.** — Orphan ADRs are invisible. (An unowned ADR fails the docs job.)
9. **Keep a source-of-truth matrix: shipped state in the changelog, the version in one VERSION file, decisions in ADRs, terms in the glossary. Do not duplicate release narratives in READMEs or agent-context files.** — Duplicates drift. (Release narratives copied into the agent-context file were retired.)
10. **Remember that doc checkers only verify; someone still writes the docs. Check the API inventory both ways (every endpoint documented, every documented endpoint real), and allow API specs to be a subset but never stale. A new endpoint means hand-editing the inventory and the API spec in the same change.** — Docs and code drift in both directions. (Checkers made forgetting visible but generated nothing.)
11. **Run a link and path checker over the gateway docs and agent-context files, including paths inside code spans, plus a structure check for required sections.** — Context files pointing at moved files mislead every later session. (Broken paths were found in agent-context files.)
12. **Have each shipped slice update the internal-docs page that owns what it changed, stamp a "verified" field with the release, and redeploy. Build internal docs strictly (links, ownership, word budgets, click depth).** — Hand-written overviews drift unless every slice touches them. (The internal docs site drifted between sessions.)
13. **Monitor the deployed docs site's version against VERSION, warning softly and never blocking a deploy.** — Published docs lag unnoticed. (A report-only check now surfaces the lag.)
14. **Keep each external ID or asset manifest in exactly one file, and drift-check every copy by format, placement and content hash, naming the command that fixes a mismatch.** — Copies drift. (Video IDs and posters were duplicated between the app and the site.)
15. *Moved to `references/packs/product.md`: tutorial videos.*
16. **File follow-up docs or video issues after the merge, based on what was actually built, after checking what the build already updated.** — Plans overestimate the docs left to do. (Only one video issue was still needed.)
17. **Mark superseded notes obsolete, with a pointer to what replaced them.** — Later readers act on dead premises. (A note about a removed race stayed in memory.)
18. **Document the known gaps in an automation's coverage instead of presenting it as complete.** — Hidden gaps get relied on. (The runbook names a missing "in-progress" label.)
19. **When trimming docs, aim for shorter and current, but never delete load-bearing content (runbook steps, gotchas, invariants, exact commands). Update every link when moving files, and let the link checker gate it.** — Aggressive trims remove operational steps. (One audit nearly did.)
20. **Keep agent-context files to operating rules. Shipped state goes in the changelog.** — Narratives bloat context and go stale. (See DC-9.)
21. **After any persisted state change, write the lesson back into this file so the next run inherits it.** — Lessons left in chat are lost. (The operator wants every learning, small to large, fed back into the skill.)
22. **Record each rejected alternative and why it lost, in the ADR or spec, so a later "why not X?" is answered from the docs instead of being re-litigated.** — Otherwise the same mistake gets tried again. (The operator asked why a wrapped engine had been preferred over the direct library and whether any record said why. The answer had to be rebuilt.)

## 18. Communication (CM)

1. **Check push and remote state with git (`git fetch`, then `git log origin/main..HEAD`) before saying anything about it, and never quote a running tally. If nothing is pending, say nothing about it.** — Stale claims annoy and mislead. (Repeated "N commits pending push" lines appeared after the operator had already pushed.)
2. **Derive elapsed-time and progress claims from git history, not from the plan calendar.** — "The truth is what happened on the ground." (An assistant claimed day 19 when git showed 3 days.)
3. **Never claim "fixed", "deployed" or "0 failed" from indirect evidence.** — Overconfident claims cost more trust than the bug. (False "deployed" and "0 failed" reports were both called out.)
4. **Know where the human actually tests. If they dogfood on staging, "test it" means deploy to staging.** — Local verification is not their reality. (Local tests kept being proposed to an operator who tested only on staging.)
5. **When the user is remote, offer a way to reach local services (a tunnel or private mesh) before telling them to run something locally, and set the env the tunnel needs.** — They cannot reach localhost. (The operator asked why no tunnel had been offered.)
6. **Rank the options and act on a clear winner: state the pick and the runner-up in one line, then start. Ask only when the ranking is close or the evidence contradicts it. Asked "what next?", open with a ranked position, not a question.** — Asking after a decisive ranking wastes the ranking. (A ranking gave 0.97 and a four-option question still followed: "Why are you not using the ranking table to decide?")
7. **End a run with a short plain-English summary: the confirmed root cause and how it was confirmed, the rankings used, what changed for the user, gate results, the commit list (`git log main..HEAD`), and exactly what the human should check by hand. Keep it short for phone readers.** — Raw transcripts are unreadable on a phone. (The operator often reviews from a phone.)
8. **Read dictated messages for intent: transcription mangles brand and product names.** — Work out the intended word from context. ("GitHub" and the brand name came through garbled.)
9. **When a manual step is needed in an external console, remind the human which account to sign in with.** — Services use different login identities. (This tripped up several manual steps.)
10. **Do not assume jurisdiction or locale from where the user lives, and do not advise outside your expertise.** — Assumptions go wrong. (A business entity was registered in another country from the one assumed.)
11. **Ask what came back from outreach or users before proposing more features.** — Demand should steer building. (The agreed posture was to wait for replies.)
12. **Treat moving tracker board cards as the agent's job (in progress at launch, staged when pushed). The human files issues, verifies and approves pushes.** — It keeps the board true without burdening the human. (The operator ratified this board model.)
13. **When the human sends you on a detour mid-task, note the original task first and return to finish it.** — Detours swallow the work they interrupted. (The operator had to add "don't forget what you went there for earlier".)
14. **Before handing the human a manual step, check whether an available tool or an authorised connection can do it. Hand over only what really needs them: a permission block, a secret, a physical device.** — Every manual step costs the human time they may not have. (After re-authorising a connector, the operator was asked to do the step by hand anyway: "Don't ask me to do it manually.")

## 19. Cost (CO)

1. **Tier models by stage: spend on judgment (diagnose, spec, plan, verify and repair at the strongest model with high effort) and save on mechanical work (build, gates, docs at a mid tier with medium effort). Never cheapen verification.** — The worst failures came from bad judgment, not from cost. (Diagnosis is only about two agents per run, so the strongest model is cheap in absolute terms.)
2. **Measure a repair-rate baseline before cheapening a stage, log tasks, repairs and code-defect rejections per run, and revert the cheaper tier if repairs rise materially.** — Tier changes are experiments. (The baseline was about 23% of build tasks needing repair, 5 of 22, at 1.3M to 2.5M subagent tokens per workflow.)
3. **Probe a model tier with a trivial instruction ("reply with exactly: ok") before allowing it any stage that can write or commit, and exclude tiers that fail.** — Cheap models can go rogue. (The smallest tier invented a task, wrote 342 lines, committed to main under the human's name without the trailer, then amended its own commit.)
4. **Stub paid external model calls in e2e and CI by default and assert zero billed calls. Keep a tiny real-API smoke test (about 2 calls) on release tags only, gate live-model suites with a skip flag locally as well as in CI, and feature-detect stub support so older branches still run.** — Tests otherwise bill on every run. (CI e2e on the real extractor drove daily API cost up several-fold, and local server tests still billed.)
